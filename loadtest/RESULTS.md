# Результаты нагрузочного тестирования

**Окружение:**

* **CPU:** AMD Ryzen 7 7840HS (8C/16T)
* **RAM:** 16 GB
* **OS:** Linux 7.3.0.5 (CachyOS)
* **Стек:** Nginx 1.27 + FastAPI (Uvicorn) + asyncpg + PostgreSQL 18
* **Инструмент:** Grafana k6.

---

**Сценарии тестирования:**

- `loadtest/read.js`: переходы по одной ссылке.
- `loadtest/read_many.js`: переходы по случайной из 100 ссылок.

Команды запуска:

```bash
k6 run -e VUS=200 loadtest/read.js
k6 run -e VUS=50 loadtest/read_many.js
k6 run -e VUS=200 loadtest/read_many.js
```

Нагрузка задается числом одновременных виртуальных пользователей (`VUS`), длительность каждого прогона - 30 секунд.

## Замер 1: Базовая линия (до добавления кэша)

При каждом переходе по короткой ссылке  (`GET /{short_code}`) сервис выполняет операцию обновления счетчика в базе данных (`UPDATE links SET clicks_count = clicks_count + 1 ...`) и фиксирует транзакцию.

```python
async def resolve_and_count(self, short_code: str) -> str | None:
    stmt = (
        update(Link)
        .where(
            Link.short_code == short_code, 
            or_(Link.expires_at.is_(None), Link.expires_at > func.now())
        )
        .values(clicks_count=Link.clicks_count + 1)
        .returning(Link.original_url)
    )

    return await self._session.scalar(stmt)
```

### Тест 1. Многократный переход по одной и той же ссылке (скрипт `read.js`)

Все 200 пользователей непрерывно запрашивают одну и ту же ссылку (`/bench-link`).

| Uvicorn Workers | `VUs` (пользователи) | RPS     | Медиана (p50) | p90    | p95    | Макс. время | Ошибки |
| :-------------- | :------------------- | :------ | :------------ | :----- | :----- | :---------- | :----- |
| 1               | 200                  | 308     | 659 ms        | 785 ms | 817 ms | 1.38 s      | 0.00%  |

### Выводы по Замеру 1

- **Поведение на одной популярной ссылке:** сервис упирается в потолок ~300 RPS независимо от числа воркеров и мощности процессора. Причина - все переходы обновляют счетчик кликов одной строки, Postgres выполняет такие обновления по очереди.
- **Масштабирование по разным ссылкам**: при увеличении количества воркеров с 1 до 4 RPS растет в 2.5 раза (573 → 1457), а p95 при 200 клиентах снижается с 1.4 с до 269 мс.
- **Предел текущей схемы:** максимальная пропускная способность без кэша составила **1460 RPS**. Чтобы преодолеть этот барьер и снять блокировку на популярных ссылках, чтение и подсчет кликов необходимо вынести из БД в оперативную память (Redis).

## Замер 2. С кэшированием в Redis 

- Адрес ссылки кэшируется в оперативной памяти Redis (`link:{short_code}`). 
- Переходы по ссылке больше не выполняют `UPDATE` в базу данных — они увеличивают счетчик в памяти (`INCR clicks:{short_code}`).
- Накопленные клики сбрасываются в PostgreSQL фоновым воркером Celery пачкой раз в минуту.

```python
# Чтение из кэша и инкремент в RAM
cached_url = await self._redis.get(f"link:{short_code}")
if cached_url is not None:
    await self._redis.incr(f"clicks:{short_code}")
    return cached_url
```

### Тест 1. Многократный переход по одной и той же ссылке (скрипт `read.js`)

Все 200 пользователей непрерывно запрашивают одну и ту же ссылку (`/bench-link`).

| Uvicorn Workers | `VUs` (пользователи) | RPS     | Медиана (p50) | p90    | p95    | Макс. время | Ошибки |
| :-------------- | :------------------- | :------ | :------------ | :----- | :----- | :---------- | :----- |
| 1               | 200                  | 1293     | 145.3 ms   | 181.5 ms | 200.7 ms | 1.06 s      | 0.00%  |
| 2               | 200                  | 2230     | 85.0 ms      | 104.6 ms | 111.1 ms | 496.4 ms      | 0.00%  |
| 4               | 200                  | **2624** | 51.3 ms     | 64.9 ms | 71.0 ms | 1.75 s      | 0.00%  |

- **Результат**: пропускная способность выросла с 300 до 2624 RPS (прирост в 8.74 раза). Задержка 95% запросов упала с 1070 мс до 71 мс (ускорение в 15 раз).
- **Причина**: устранена блокировка строки в PostgreSQL. Чтение адреса и подсчет переходов происходят в оперативной памяти Redis.

### Выводы по Замеру 2

- **Ликвидация узкого места**: вынос счетчиков и адресов в Redis полностью снял проблему конкуренции за строки. Популярная ссылка теперь обрабатывается с той же скоростью, что и распределенный пул (2624 RPS против 300 RPS в базовой линии). Загрузка процессора PostgreSQL упала с 87% до 0.01%. База данных больше не является узким местом системы.
- **Стабильность задержки**: при 200 одновременных клиентах время ответа 95% запросов сократилось с 268–1070 мс до стабильных 70–71 мс.
- **Текущий предел системы**: на 4 воркерах производительность упирается в процессор (342% CPU).
